RideWheelShare — Production N+1 & Performance Analysis

Read-only code investigation · App root: /var/www/app.ridewheelshare.com · Laravel 9.52 / PHP 8.2 · Prepared: 2026-07-28 · For: Development Team

Why this report exists: The production app server (t3.xlarge) hits 100% CPU every business day. On Jul 27: 399,559 requests, 1,016 × HTTP 503 and 273 × HTTP 500 served to users. ALB-measured cost ranking shows GET api/driverbooking/{id} at 9–11 seconds per call (~28 CPU-hours that day alone). Database is idle (RDS at ~5%); all time is burned in PHP executing per-row query loops (N+1). ProxySQL digest stats over 26 days: 143M single-key user_meta lookups, 97M role display-name joins, 43M ride_status lookups.

2. Exact N+1 Locations

2.1 GET api/driverbooking/{id} — PRIMARY CPU OFFENDER (9–11 s/call)

Upfront global loads (AuthController.php L190–193): getAllUsersByRoleReporting() is called three times (Facility, Customer, Driver). Helper at app/helpers.php:53–63:

function getAllUsersByRoleReporting($roleName) {
    $users = App\Models\User::whereHas(
        'roles', function($q) use ($roleName) {
            $q->where('name', $roleName);
        }
    )->with('usersMetas')
    ->get();
    return $users;
}

That loads all users of that role system-wide + all their user_meta rows on every request — and the response also returns the full $customers collection (L254).

Per-booking loop (AuthController.php L195–249):

If limit/offset are omitted, the else branch (L161–187) loads every non-cancelled booking for the driver, multiplying the above by N. Estimated: ~1 booking SELECT + 3 role/whereHas loads + eager meta + ~5N queries. For N≈500–2000 → thousands of queries → matches the observed 9–11 s.

2.2 POST api/appdashboardcalenderlistingday

Main booking fetch already uses JOINs on user_meta (good). The N+1 is the role display-name lookup inside every booking iteration (AuthController.php L1495–1509):

$rolebookingcreatename = DB::table('role_user')
    ->join('roles', ...)->join('users', ...)
    ->where('role_user.user_id', $booking->created_by)
    ->selectRaw("CONCAT(...) as display_name")
    ->value('display_name');

Repeated at L1509, L1749, L2012 (TM / Driver / Facility branches) and in the week/month sibling methods (L2317, 2573, 2888, 3152, …). This is the smoking gun for ~97M role display-name joins. Also: whereHas('roles') for driver/facility lists (L1285+, L1553+) and nested foreach ($facilities) per booking (PHP-side CPU).

2.4 POST api/dashboardappnew

Facility/TM paths: fixed set of COUNT/SUM/JOIN queries (~5–7). Latency (~500 ms × 23k/day) driven by heavy aggregates on bookings + role_user joins, not per-row loops. Superadmin/else path (L14126+) loads getAllTransactions()/getAllExpenses() and sums in PHP — heavy but rarely hit by mobile polling.

2.5 POST api/pendingapplistingapidata

Already batched via JOINs — no per-row loops. Cache bug: L3415–3419 performs Redis::set + expire(60) but there is no Redis::get anywhere under app/ or routes/. Every request still hits the DB; the Redis write adds load without ever serving a read.

2.6 Polling web endpoints

  • checkNewBookings: Booking::getBookingsWithoutDrivers() loads the full row collection then ->count() in PHP (Booking.php L82–103; controller L1746). Also lazy-loads Auth::user()->roles.
  • checkNewBookingsNemt: one COUNT join — OK; still lazy-loads roles.
  • fareupdatenotify: single exists() — fine.

9. Priority Order for Implementation

  1. Rewrite AuthController::driverbooking (global user dumps + 4× UserMeta + RideStatus per row) — sole explanation for the 9–11 s response time.
  2. Batch/join creator display_name in calendar day/week/month methods.
  3. Fix drivercolorapi meta N+1.
  4. Replace write-only Redis with Cache::remember on dashboard / pending / color endpoints.
  5. Fix getBookingsWithoutDrivers to a COUNT query.
  6. Add missing Eloquent relations (UserMeta→User, RideStatus→Booking, Safetybookingcheck→Booking, Booking→facility/driver/rideStatus/creator) so future code can eager-load instead of querying imperatively.
